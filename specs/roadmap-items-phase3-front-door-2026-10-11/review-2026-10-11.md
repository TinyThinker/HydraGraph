# Review of the Phase 3 front-door spec

Date: 2026-10-11

The plan was checked against the code and found mostly sound. Line references, file
sizes, the CSP, and the "no Dexie bump" rule all match. The items below were changed
in the phase files. Each item says what the original plan said, what was wrong, and
what changed.

## Must fix

**1. Turns can freeze on "generating" when the disk is full**
- **Plan said:** fix `persistError`, the code that runs when a reply fails.
- **Problem:** the code that runs when a reply *succeeds* (`finalizeNode`) has the same
  flaw. It saves to the database first, then updates the screen. If the save fails
  because browser storage is full, the screen update never happens. The turn shows
  "generating" forever, and the error goes nowhere. This is the most likely save to
  fail, because it runs at the end of every turn. The Stop button's code
  (`cancelGeneration`) has the same flaw.
- **Change:** fix all three the same way — update the screen first, then save, and
  catch any save error. (Phase 1, task 1.2.)

**2. Typing a key in Settings can get erased**
- **Plan said:** store the new backup-tracking values in the settings record.
- **Problem:** the Settings window reloads its fields every time the settings record
  changes. Phase 2 starts writing to that record in the background (e.g. when a turn
  finishes). If that happens while someone is pasting a key, the field resets and the
  unsaved key is gone.
- **Change:** load the fields once when the window opens, not on every change.
  (Phase 2, task 2.2.)

**3. Chrome may block Ollama for a reason the plan didn't mention**
- **Plan said:** if the Ollama test fails, it's either a missing `OLLAMA_ORIGINS` or
  Ollama not running.
- **Problem:** since late 2025, Chrome asks the user for permission before a website can
  talk to programs on their own computer. If the user clicks "Block", the failure
  looks exactly like the other two.
- **Change:** list this as a third cause in the error message and the Ollama hint. The
  "Test connection" button is a good place for Chrome's prompt to appear first.
  (Phase 3, design decisions and tasks 3.4, 3.7.)

**4. The OpenRouter check used an old address**
- **Plan said:** check the key at `/auth/key`.
- **Problem:** OpenRouter's docs now list `/key`. The old one may still work, but it's
  not the documented one.
- **Change:** use `/key`. (Phase 3, design decisions.)

## Should fix

**5. Exporting one tree silenced the reminder for all trees**
- **Plan said:** save one "last exported" date; remind if it's too old.
- **Problem:** export saves one tree at a time. Export tree A, and the reminder goes
  quiet even though trees B and C were never backed up. Also, the reminder fired even
  when nothing changed since the last export — that's nagging.
- **Change:** keep an export date per tree. Remind only if that tree changed since its
  last export. (Phase 2, tasks 2.2, 2.4, 2.5.)

**6. The app asked the browser to keep data only once**
- **Plan said:** ask once, remember the answer forever.
- **Problem:** Chrome decides based on how much you've used the site. "No" on day one
  can become "yes" by day ten. Asking once locks in the early "no".
- **Change:** ask again once per visit until the answer is yes. Also note Firefox shows
  a real pop-up when asked, so expect it after turn 3. (Phase 2, task 2.3.)

**7. The test result had no clear home**
- **Plan said:** the "Test connection" button keeps its own result.
- **Problem:** two other pieces need that result — the Ollama hint (opens itself on
  failure) and the step indicator (ticks step 3 on success). They can't see a result
  hidden inside the button.
- **Change:** keep the test result in the Settings window and pass it to all three.
  That means the Settings file grows over three tasks, so split it once, at the first
  task that touches it. (Phase 3, tasks 3.2–3.4.)

**8. One planned test couldn't be built**
- **Plan said:** confirm the storage-full error's shape with a real test.
- **Problem:** tests use a fake database that never runs out of space, so it can't
  produce a real storage-full error.
- **Change:** build fake errors from Dexie's own error types, and also catch the older
  form of the error that some browsers still raise. (Phase 1, task 1.1.)

## Minor

- **Step 2 for Ollama:** the plan said "non-default URL or any URL", which contradicts
  itself. The URL is pre-filled, so use "URL is not empty". The test (step 3) is the
  real check.
- **"Protected by browser" label:** promises too much on Safari, which can still delete
  data (the plan's own notes say so). Use "Browser agreed to keep this data. Still
  export."
- **"Free space" in the storage-full banner:** the app gives no way to do that. Storage
  mostly runs out in private windows. Say "delete trees you don't need, or leave
  private browsing."
- **"A returning user can't be detected":** slightly overstated — a cookie set by the
  server would survive Safari's cleanup. But that needs server setup, and the plan's
  simpler fix (an "Import a backup" link on the demo) is still the right call. Just
  soften the wording.

## What changes overall

- **Phase 1** gets bigger: it fixes three stuck-turn bugs instead of one.
- **Phase 2:** the reminder becomes per tree and only fires when there's unsaved work.
  The browser keeps getting asked until it agrees. Settings stops erasing what you
  type (one small fix).
- **Phase 3:** error messages mention Chrome's permission prompt, use the new
  OpenRouter address, and the test result moves up to the Settings window.
- **Unchanged:** phase order, task boundaries, no database migration, the demo-banner
  recovery link.
